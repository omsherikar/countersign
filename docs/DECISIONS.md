# Decisions

Numbered, dated, with the reason. Newer entries at the bottom. Nothing here is deleted; a reversed decision gets a new entry pointing back.

## D1. Python 3.12 in every container (2026-10-28)
networkx 3.7 excludes 3.14.1 and openmined.psi wheels stop at CPython 3.13. 3.12 has a wheel for every library in the spec. `uv` manages each Python project; `uv.lock` is committed.

## D2. Next.js 16 App Router, Tailwind v4, shadcn/ui, TanStack Query, Recharts, pnpm (2026-10-28)
Matches the spec and the team's existing stack. No Vite.

## D3. One Postgres 17 instance, three databases (2026-10-28)
`countersign` (api), `mockgov` (mock government systems), `countersign_test` (pytest). mockgov is a separate process with no import path into the api; the api reaches it only over HTTP through adapters. This keeps the "swap mock for real" story honest.

## D4. Auth is email + password, argon2, short-lived JWT in an httpOnly cookie (2026-10-28)
One `users` table with a role and optional scope columns (institution, region, student, university). RBAC lives in FastAPI dependencies, never only in the UI.

## D5. Three adapter implementations per government source (2026-10-28)
`InMemory*` for unit tests, `MockGov*` for the demo (HTTP to services/mockgov), `Real*` with the same interface that raises unless `ALLOW_REAL_GOV_APIS=true`, which is never set. Selected by `GOV_ADAPTER`.

## D6. The whole schema lands in Week 1 (2026-10-28)
Every core table from the spec is in migration 0001 so later weeks add engines and columns, not tables.

## D7. Audit hash chain from day one (2026-10-28)
`audit.record()` runs in the same transaction as the write it describes and chains `sha256(prev_hash + canonical_json)`. The "verify chain" button is Week 3; the chain itself cannot be retrofitted.

## D8. No India map; a state grid instead (2026-10-28)
A wrong boundary in front of a government panel is a disaster. A map comes back only in Week 4 and only from a Survey of India-compliant source.

## D9. APAAR at rest: HMAC for lookup, Fernet copy, last four digits (2026-10-28)
The full ID never leaves the api. Mobile and address get the same HMAC treatment.

## D10. Seat-pool percentages come from the handbook text, not memory (2026-10-28)
Verified against the APH 2024-27 PDF and the 2026-27 addendum. `rules.yaml` carries a `source:` per value: NRI 5% within intake (cl. 2.8b), TFW 5% supernumerary (cl. 6.42d), lateral 10% supernumerary plus first-year vacancies (cl. 6.13a,f), international 15% Engg Diploma/UG, 25% Engg PG, 25% Management/MCA/Design/Planning/HMCT/Applied Arts all levels (cl. 2.9 + 2026-27 addendum), one third of international seats for CIWG, FN via supernumerary plus lateral capped at 15% (cl. 6.13b). EWS 10% is a reservation category, not a pool (cl. 4.6).

## D11. Tests run inside compose (2026-10-28)
`make test` runs pytest in the api, mockgov and datagen containers against `countersign_test`. Nobody needs a local Postgres.

## D12. Datagen is deterministic and never writes to the api database (2026-10-28)
It writes what a college would upload (CSV/XLSX), the mockgov registries, demo users and `ground_truth.json`. `make seed` loads them through the api's own importer. From Week 2 student rows go through the real upload engine.

## D13. Parallel build with role-split agents on separate branches (2026-10-28)
Backend, frontend, UI, UX, progress and monitor roles each work on their own branch from a shared contract in `docs/ARCHITECTURE.md` and `docs/API_CONTRACT.md`. The contract is the only thing both sides may assume about each other.

## D14. An upload is a delta keyed by student identity (2026-10-28)
An upload carries one institution and one academic year and touches only the rows it contains. Each row upserts the enrolment keyed by (student identity, programme, academic year). Identity is the APAAR HMAC when a valid APAAR is given with consent, else the passport HMAC for an international student, else the institution's provisional match on normalised name, date of birth and mobile HMAC. Three optional columns, `status` (ACTIVE by default, WITHDRAWN or TRANSFERRED), `status_date` and `admission_date` (both ISO dates, defaulting to the upload date), let a college report withdrawals, transfers and late admissions without re-sending its roll. Re-uploading the same file changes nothing, and a bad row never aborts a file: it becomes an upload row error and the good rows proceed. Reason: colleges change their rolls all year; a delta with stable identity keys makes re-uploads safe and lets the Seat Ledger see releases and refills as events.

## D15. One pipeline function with a fixed stage order (2026-10-28)
`run_batch(batch_id)` runs parse and header check, row validation, within-file duplicates, upsert of students and enrolments, Seat Ledger, the five checks (adapter calls concurrent), cross-institution duplicates, flags, then marks the batch DONE with counts. The Celery task, the REST upload path and `make seed` all call it. Progress (`stage`, `total_rows`, `processed_rows`) is saved on `upload_batches` every 500 rows. Reason: one code path means the seeded demo and a live upload behave the same, and the order guarantees each engine finds what it depends on (checks need seats; duplicates need upserted students).

## D16. The Seat Ledger assigns seats in the database (2026-10-28)
The admission route picks the pool through `rules.yaml` `admission_routes`; the approval is the one for (programme, cohort year) from `app/core/cohort.py`. A seat is taken in one transaction with `SELECT ... FOR UPDATE SKIP LOCKED LIMIT 1` on FREE seats of that pool; CIWG-reserved seats go only to CIWG students and the INTERNATIONAL pool only to the INTERNATIONAL route. With no free seat the enrolment stays unseated and a flag is raised once per (institution, programme, cohort year, pool): EXCESS_ADMISSION (HIGH) for the REGULAR pool, QUOTA_BREACH for any other pool (MEDIUM, HIGH when INTERNATIONAL or NRI is exceeded by more than 2). Its evidence is refreshed as rows arrive ("132 admitted against 120 approved; 12 without a seat"). WITHDRAWN and TRANSFERRED release the seat back to FREE. A released seat assigned again after the approval's cutoff date (judged by `admission_date`) raises LATE_REFILL (MEDIUM). Seat events are append-only and every assignment and release is written to the audit chain. Reason: when every approved seat is a row, excess and quota breaches are counted by the database the moment a file lands; SKIP LOCKED keeps concurrent workers safe; the event log plus the hash chain give officers a tamper-evident seat history.

## D17. Name matching is a pure, heavily tested module (2026-10-28)
`app/engine/matching.py` normalises names (lower case; honorifics mr, ms, mrs, dr, shri, smt, kumari, km and sri removed; punctuation stripped; spaces collapsed; Mohd, Md, Mohammad and Muhammad folded to mohammed; common spelling folds), transliterates Devanagari to Latin with indic-transliteration (ITRANS or IAST, then ASCII-folded) and matches tokens with awareness of initials on top of RapidFuzz, so "R. K. Sharma" and "Ravi Kumar Sharma" score at least 90 when the initials line up and the surname matches. Thresholds come from `rules.yaml`: 90 and above is a match, 75 to 90 needs review, below 75 is no match. Date of birth must agree for any identity or duplicate decision. Reason: Indian names arrive with honorifics, initials, spelling variants and in Devanagari, and plain fuzzy ratios score them too low; pure functions are cheap to test exhaustively, and thresholds in `rules.yaml` keep the cut-offs visible to the panel.

## D18. Five checks with fixed outcomes; an outage is never a failure (2026-10-28)
Each check in `app/engine/checks/` returns a status, a source and a detail with a plain-English `summary`. IDENTITY verifies the APAAR (NA without one, FAIL with INVALID_APAAR or NAME_MISMATCH, PENDING for review between 75 and 90). ADMISSION checks the counselling list for counselling, TFW and lateral admissions, the seat-type rules for management, spot and NRI admissions, and Study in India for international ones. SEAT passes when the enrolment holds one assigned seat in its cohort approval. STUDYING reads ABC credits for each completed year, from year 2 for a lateral entrant (NA in the first year, for a year-2 lateral entrant or without an APAAR; FAIL with NO_ACADEMIC_ACTIVITY when two or more expected semesters have no credits; PENDING when one does). STUDENT stays PENDING until the Week 3 student loop. A source that cannot be reached gives PENDING with `detail.source_unavailable`, never FAIL, and the recheck endpoints re-run PENDING checks. Score is passes over applicable checks (not NA); PENDING counts as applicable but not as a pass, shown as "n of m". Reason: one independent source per check lets an officer see exactly which source disagreed, and treating an outage as pending means a government system going down never flags a genuine student.

## D19. Duplicates: exact within a file, blocked and fuzzy elsewhere (2026-10-28)
`app/engine/duplicates.py`. An APAAR repeated within one file is a row error, DUPLICATE_IN_FILE, and the later row is rejected. Within an institution, records without an APAAR are blocked on (date of birth, first initial, metaphone of the surname) and a pair whose names score 90 or more with initials awareness, or that share a mobile HMAC, raises DUPLICATE_WITHIN_UPLOAD (MEDIUM) linking both enrolments (the "R. K. Sharma" demo). The same APAAR ACTIVE at two institutions in one academic year raises DUPLICATE_CROSS_INSTITUTION (HIGH), unless one programme is PHYSICAL and the other ODL or ONLINE, which raises DUAL_ENROLMENT_ALLOWED (LOW) and cites the UGC 2022 rule. Without an APAAR across institutions, the same block plus a name score of 90 or more plus the same mobile HMAC raises DUPLICATE_CROSS_INSTITUTION (MEDIUM). This needs `programmes.mode` (migration 0002); the seed imports datagen's `mode`. Reason: a repeated id inside one file is a clerical error the college fixes itself, while everything across records needs evidence and an officer; blocking keeps comparisons near linear; and the UGC rule makes one physical plus one distance programme lawful, so it must not read as a duplicate.

## D20. Flags are made by engines, deduplicated and never deleted (2026-10-28)
Only engines create flags. Each carries a `dedupe_key`, so a re-run updates the existing flag instead of adding one; flags are never deleted and start OPEN. Evidence has one schema: `{summary, facts: [{label, value, source}], related_enrolment_ids, rule_source?}`, where `summary` is one plain-English sentence from the copy deck templates. Week 2 exposes read endpoints only; officer actions arrive in Week 3. Reason: an officer must be able to trust that a flag reflects the data and was not added or removed by hand; dedupe keys make every engine safe to re-run; one evidence shape lets the web render any flag without special cases.

## D21. Dashboard KPIs from real flags and checks (2026-10-28)
`kpis.flags_open` counts real flags. `kpis.countersigned_pct` is the share of ACTIVE enrolments whose applicable checks are all PASS; `kpis.clear_pct` is the share with no FAIL. The institutions list sort `flags_open_desc` becomes real. Reason: the share fully countersigned is the headline number; with the student check pending until Week 3 it stays below 100 percent, which is the true state, and the clear share shows how much of the roll no source contradicts.

## D22. The seed goes through the engine, against a time budget (2026-10-28)
`make seed` seeds mockgov first, then runs every datagen upload through `run_batch` in-process (no Celery), so the Makefile order changes. Target: the small seed (about 10.5k rows) in under 3 minutes. 50k rows in under 2 minutes is the Week 4 evaluation target; it is measured and recorded now. Reason: the demo data must come from the same engine the panel is shown, and measuring early tells us whether Week 4 needs bulk paths.

## D23. Every active enrolment gets a student notice after its upload (2026-10-28)
When an upload batch reaches DONE, a separate background task (`countersign.send_notices`) sends the notices, so finishing a batch is never delayed by mail. Every ACTIVE enrolment in the batch that has no live or answered notice gets one, whatever its Identity result. A notice goes by email when the college gave an email address and to the student's DigiLocker inbox when the student has a linked APAAR; each channel has its own row and its own link token (32 random bytes, URL-safe), of which only the SHA-256 hash is stored. Links read `{WEB_ORIGIN}/student/notices/{token}` and expire after `notices.expiry_days` in `rules.yaml` (30). Each delivery is recorded as QUEUED, SENT or FAILED and tried up to three times with a pause between tries; a DigiLocker outage never holds up email, and a DigiLocker answer that the APAAR has no account marks that delivery FAILED. The mailer refuses any SMTP host outside `SMTP_ALLOWED_HOSTS` (by default `mailpit`, `localhost` and `127.0.0.1`) unless `ALLOW_REAL_SMTP=true`, which the project never sets, and opens one SMTP connection per 500 messages. When an enrolment has no live notice and no reply (every notice expired or failed), the college (for its own students) or an officer may resend it, at most three times per enrolment and academic year. A student who has withdrawn notice consent gets no new notices. Reason: the notice is how the real APAAR holder learns that their identity was used, so it must reach the student even, and especially, when Identity failed; storing only a hash means a copy of the database cannot answer a notice; and the SMTP allow-list, like the rule for government APIs, keeps the demo from ever writing to a real person.

## D24. The Student check comes only from the notices, and a No beats a Yes (2026-10-28)
The STUDENT check (source `STUDENT_NOTICE`) is derived from the enrolment's notices, never from an adapter. No notice sent yet, a notice sent and not answered, and a notice that expired without a reply all leave it PENDING with a neutral sentence: no reply is never a failure and never a flag. A Yes on any channel makes it PASS. A No on any channel makes it FAIL and raises STUDENT_DENIED (HIGH, one per enrolment), and a No beats a Yes, because the college supplies the email address while DigiLocker is tied to the APAAR holder. The flag's evidence gives the channel, the date the notice was sent and the date of the reply; the student's comment is a fact for officers only, so a registrar never sees it. The student may change an answer once within 7 days of the first reply. No to Yes makes the check PASS, but the flag keeps its status (only officers resolve flags) and gets refreshed evidence and a system note in its history; Yes to No makes the check FAIL and raises the flag. The countersign score and the dashboard use the new status at once. A Yes also records the student's notice consent. Reason: silence proves nothing either way, so it must never count against a genuine student; a denial is the strongest sign of identity misuse the product can collect, so it goes to an officer with the student's own words; and a short window to correct a mistaken tap stops one slip from turning into a case while the officer still sees what happened.

## D25. Officers act on flags through a fixed table of transitions (2026-10-28)
Officers act with `POST /flags/{id}/actions`, giving an action and a note (only ASSIGN may omit the note). From OPEN or DOCS_REQUESTED a flag can move to DOCS_REQUESTED (request documents), ESCALATED, CLEARED or CONFIRMED. From ESCALATED only an AICTE officer can move it to DOCS_REQUESTED, CLEARED or CONFIRMED. CLEARED and CONFIRMED are final, except that an AICTE officer may reopen a flag, with a note, which sends it back to OPEN. Adding a note and assigning an officer never change the status. A regional officer acts on flags of institutions in its region, but on an escalated flag may only add notes. A college may only respond, with a note and up to three PDF, PNG or JPEG files of at most 5 MB each, while its own flag is DOCS_REQUESTED; the response keeps that status and marks the flag as answered. Universities never act on flags. A wrong role gets 403, a flag outside the caller's scope 404, and a move the table does not allow 409 `FLAG_TRANSITION_INVALID`. Requesting documents emails every registrar of the college and records the due date on the flag. Confirming changes nothing on the enrolment and deletes nothing; it revokes any active credential issued for the flag's enrolment, and the confirmation sheet says so. Engines still never change a flag's status; when they refresh the evidence of a cleared or confirmed flag, a system note says so in the history. Attachments are stored outside the database under random names with their SHA-256 and are served only through a scoped, audited download. Every action is a `case_actions` row, so a flag's history shows who did what, when and why. Reason: a fixed table with role rules makes the case record predictable and testable; an escalation means a senior officer takes over, so the regional office cannot quietly undo it; and leaving the enrolment untouched on confirmation keeps the rule that nothing is auto-rejected, with the decision recorded instead.

## D26. Student-held credentials are SD-JWTs signed by Countersign (2026-10-28)
Credentials use the `sd-jwt` reference library (SDJWTIssuer, SDJWTHolder, SDJWTVerifier) with ES256 keys from `jwcrypto`. The issuer key is a `signing_keys` row whose private part is Fernet-encrypted with `PII_FERNET_KEY` and whose `kid` is the JWK thumbprint; it is created on first use and only one is active. The issuer publishes `/.well-known/jwks.json`, `/.well-known/jwt-vc-issuer` (`{issuer, jwks_uri}`) and an IETF Token Status List at `/status-lists/1` (one bit per credential, 131,072 entries, compressed and cached for 60 seconds); the issuer URL comes from `ISSUER_URL`. An Enrolment proof is issued automatically when the enrolment's Student check is PASS, no check is FAIL and no unresolved HIGH flag names the enrolment; eligibility is looked at again after a recheck and after a case is cleared, and there is at most one active credential per enrolment and kind. The signed claims always in view are the issuer, issue time, expiry (31 August after the academic year ends), the credential type `countersign:enrolment:v1`, the status-list entry and the holder's public key; name, date of birth, masked APAAR, institution, programme, academic year, year of study and the list of countersigned checks with their date are selectively disclosable. Each student has an ES256 holder key, kept encrypted on the server because the demo wallet is custodial; a real deployment keeps it on the student's phone. To share, the student ticks fields and agrees to the share text, and the server builds the presentation with institution and programme always disclosed and a key-binding JWT whose nonce is a one-time share code (six groups of four Crockford base32 characters) and whose audience is `{ISSUER_URL}/verify`; it is kept for 10 minutes and returned as a code, a link and a QR. A credential's status-list index is a random unused one. A credential is revoked when its enrolment is withdrawn or transferred, when a flag on its enrolment is confirmed, or by an AICTE officer with a reason, and never because a check is pending. Reason: selective disclosure lets a student prove an enrolment to an employer without handing over the whole record; a standard format with published keys lets anyone verify a proof without querying Countersign about the student; and a status list shows revocation without telling a verifier who else holds a credential.

## D27. Anyone can verify a proof without an account (2026-10-28)
`GET /verify/{code}` is public and rate-limited. It loads the stored presentation and checks it with the library's verifier, using a key lookup that reads the same JWKS document a third party fetches, with the share code as the expected nonce and `{ISSUER_URL}/verify` as the expected audience; it then checks the expiry and the status-list bit. `POST /verify` checks a pasted raw SD-JWT presentation the same way (issuer signature, key binding signature, expiry, status) and reports its nonce without enforcing it. The answer is VALID, REVOKED, EXPIRED or INVALID, with the credential kind, the issuer, the issue date, the disclosed fields with their labels, whether the proof is bound to the holder's key and when the status was checked. The verifier never returns a claim the student did not disclose, never a full APAAR, and offers no search. Each verification is counted on the presentation, so the student's wallet shows "Shared with a verifier at 10:42". The web page scans with the browser's BarcodeDetector where it exists and otherwise takes a typed or pasted code. Reason: an employer or admissions office should need nothing but a phone to check a proof; tying the key binding to the one-time code stops a copied presentation from being replayed under another code; and returning only what the student chose keeps the student in control of what is shown.

## D28. Degrees carry a masked APAAR and a compact signed QR (2026-10-28)
Graduates are seeded from datagen `graduates.jsonl`: final-year students of 2025-26 at institutions affiliated to each university, stored as GRADUATED enrolments of 2025-26 with no seat, no checks and no flags; most have an APAAR and a few only a provisional id. A university lists the graduates of its own affiliates (an AICTE officer sees all) with `GET /university/graduates` and issues a Degree proof with `POST /university/degrees/{enrolment_id}/issue`. The proof is an SD-JWT in the student's wallet without a holder key, because a printed proof cannot be bound to a phone, plus a compact JWS (ES256, the issuer key, `kid` in the header) over `{v, cid, n, p, i, u, y, a}`: version, credential short id, name, programme short name, institution short name, university code, year of award, and the last four APAAR digits or a masked provisional id. The QR encodes `{WEB_ORIGIN}/verify/d/{jws}`, about 350 characters, so it stays small enough to print and scan. `GET /verify/d/{jws}` checks the signature against the JWKS and the credential's revocation bit. `GET /university/degrees/{enrolment_id}` returns the print data with the QR as SVG, and `GET /university/degrees/{enrolment_id}/insert.pdf` renders a sample A4 degree insert (reportlab) with the masked APAAR and the QR. The web print view is `/university/degrees/[enrolmentId]/print`. Reason: a degree certificate is read offline by people with no Countersign account, so its QR must carry a self-contained signed claim; keeping the payload short keeps the printed code legible; and the masked APAAR lets a reader match the paper to the person without exposing the full id.

## D29. Sensitive reads join the audit chain, and the chain can be checked in the browser (2026-10-28)
Writes have been chained since D7. Week 3 adds READ entries for notice page views (no actor, marked as coming through the notice link), credential reads and shares, verifier calls (no actor, with a keyed hash of the caller's IP address), attachment downloads, enrolment detail views and student data exports. `GET /admin/audit` gains `entity_id`, `action` and `seq_from` filters, and `GET /admin/audit/verify` keeps reporting `first_broken_seq`. The AICTE officer's `/admin/audit` page lists the chain, has a Verify chain button and highlights the first broken entry. For the demo, `make audit-tamper SEQ=n` edits one stored entry from the command line and refuses unless `DEMO_MODE=true`; `make demo-reset` rebuilds a clean chain. Reason: privacy by design means being able to show who looked at a student's record, not only who changed it; and editing one entry in front of the panel is the only convincing way to show that the chain detects tampering.

## D30. Consent is stored with its exact text, and students can act on their own data (2026-10-28)
`consents` rows record APAAR linking from the college's upload (the college upload channel), notice consent when the student answers Yes, and share consent every time a proof is shared, each with the exact text shown and its `notice_version`. The privacy notice is versioned in `app/privacy/notice.py` and served publicly at `GET /privacy/notice`. A student lists their consents with `GET /students/me/consents` and may withdraw notice consent (no new notices; notices already sent can still be answered) or share consent (every live proof expires at once). Unlinking an APAAR is a correction request, because the college must upload the record again, and admission is never blocked. `GET /students/me/access-log` lists the READ entries about the student and their enrolments with the reader's role and the date only, never a name. An access request is fulfilled at once by `GET /students/me/export.json`, everything held with the APAAR masked. Correction and erasure requests go to AICTE officers through `GET /data-requests` and are resolved as DONE or REJECTED with a written response; an erasure response explains which records the law requires AICTE to keep. Masking stays everywhere. Reason: the DPDP Act gives students rights of access, correction and withdrawal that must be usable, not only described, and keeping the exact text a student saw is the only way to show what they agreed to.

## D31. The seed sends real notices and applies simulated replies (2026-10-28)
`make seed` loads mockgov, imports the institutions, runs every upload through `run_batch`, imports the graduates, sends the notices for every batch (Mailpit and the mock DigiLocker inbox), and then runs `python -m app.seed.replies --from /data/generated`, which applies datagen's `notice_replies.jsonl` through the same service the public notice page uses (no actor, marked as the demo seed). About 70 percent of clean enrolments answer Yes, every planted denial answers No, and the rest do not reply. Ravi Kumar Sharma (the `student@demo` login) and one more named student are left unanswered so the demo can answer live from Mailpit. Mailpit keeps 20,000 messages. Ground truth gains nothing: the STUDENT_DENIED cases (8 in the small size) were already planted, and the quick check must still find every planted case with no unexplained flag. Reason: the countersigned share on the dashboard and the denial cases should come from the same code a real reply takes, and leaving the demo student unanswered keeps the live moment in the demo.

## D32. Public rate limits and the Week 3 error codes (2026-10-28)
Public routes are limited per client address: `/notices/*` 30 requests a minute, `/verify` and `/verify/*` 60, `/.well-known/*` and `/status-lists/*` 120. New error codes: `NOTICE_NOT_FOUND` (404, the same body for a malformed and an unknown token), `NOTICE_EXPIRED` (410), `NOTICE_ALREADY_CHANGED` (409), `FLAG_TRANSITION_INVALID` (409), `ATTACHMENT_TOO_LARGE` (413), `ATTACHMENT_TYPE` (415), `CREDENTIAL_NOT_ELIGIBLE` (409), `CREDENTIAL_REVOKED` (409), `PRESENTATION_NOT_FOUND` (404), `RESEND_LIMIT` (429) and `NOTICE_LIVE` (409). Reason: notice links and share codes can only be guessed by brute force, and the limits make guessing pointless; giving the same answer for malformed and unknown tokens tells an attacker nothing; and one code per situation lets the web show the right sentence without reading messages.

## D33. The demo path is an end-to-end test (2026-10-28)
Playwright tests in `apps/web/e2e` drive the demo path against the running stack with Playwright's bundled Chromium, never an installed Chrome (`channel: "chrome"` is not used): every role signs in; the ABC College CSE excess flag; the R. K. Sharma duplicate; Ravi's notice is opened from Mailpit's API and answered Yes, his Enrolment proof appears, three fields are shared and the code verifies as VALID; a No on another notice raises STUDENT_DENIED; an officer requests documents, the registrar responds with a PDF and the officer clears the flag; the university prints a degree insert and its QR verifies; and the AICTE officer verifies the audit chain. `make e2e` runs the suite against the stack that `make up` started. Reason: the panel demo is the path that matters most, and only an end-to-end run shows that a change in one service has not broken a step that depends on another.
