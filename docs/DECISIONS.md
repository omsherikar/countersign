# Decisions

Numbered, dated, with the reason. Newer entries at the bottom. Nothing here is deleted; a reversed decision gets a new entry pointing back.

## D1. Python 3.12 in every container (2026-10-28)
networkx 3.7 excludes 3.14.1 and openmined.psi wheels stop at CPython 3.13. 3.12 has a wheel for every library in the spec. `uv` manages each Python project; `uv.lock` is committed.

## D2. Next.js 16 App Router, Tailwind v4, shadcn/ui, TanStack Query, Recharts, pnpm (2026-10-28)
Matches the spec and the team's existing stack. No Vite.

## D3. One Postgres 17 instance, three databases (2026-10-28)
`countersign` (api), `mockgov` (mock government systems), `countersign_test` (pytest). mockgov is a separate process with no import path into the api; the api reaches it only over HTTP through adapters. This keeps the "swap mock for real" story honest.

## D4. Auth is email + password, argon2, short-lived JWT in an httpOnly cookie (2026-10-28)
One `users` table with a role and optional scope columns (institution, region, student, university). RBAC lives in FastAPI dependencies, never only in the UI.

Partly superseded by D37 on 2026-10-29: a student signs in only through DigiLocker; every other role keeps email and password.

## D5. Three adapter implementations per government source (2026-10-28)
`InMemory*` for unit tests, `MockGov*` for the demo (HTTP to services/mockgov), `Real*` with the same interface that raises unless `ALLOW_REAL_GOV_APIS=true`, which is never set. Selected by `GOV_ADAPTER`.

## D6. The whole schema lands in Week 1 (2026-10-28)
Every core table from the spec is in migration 0001 so later weeks add engines and columns, not tables.

## D7. Audit hash chain from day one (2026-10-28)
`audit.record()` runs in the same transaction as the write it describes and chains `sha256(prev_hash + canonical_json)`. The "verify chain" button is Week 3; the chain itself cannot be retrofitted.

## D8. No India map; a state grid instead (2026-10-28)
A wrong boundary in front of a government panel is a disaster. A map comes back only in Week 4 and only from a Survey of India-compliant source.

Confirmed by D46 on 2026-10-29: Week 4 has no map either; every chart is a bar chart with its table beside it.

## D9. APAAR at rest: HMAC for lookup, Fernet copy, last four digits (2026-10-28)
The full ID never leaves the api. Mobile and address get the same HMAC treatment.

## D10. Seat-pool percentages come from the handbook text, not memory (2026-10-28)
Verified against the APH 2024-27 PDF and the 2026-27 addendum. `rules.yaml` carries a `source:` per value: NRI 5% within intake (cl. 2.8b), TFW 5% supernumerary (cl. 6.42d), lateral 10% supernumerary plus first-year vacancies (cl. 6.13a,f), international 15% Engg Diploma/UG, 25% Engg PG, 25% Management/MCA/Design/Planning/HMCT/Applied Arts all levels (cl. 2.9 + 2026-27 addendum), one third of international seats for CIWG, FN via supernumerary plus lateral capped at 15% (cl. 6.13b). EWS 10% is a reservation category, not a pool (cl. 4.6).

## D11. Tests run inside compose (2026-10-28)
`make test` runs pytest in the api, mockgov and datagen containers against `countersign_test`. Nobody needs a local Postgres.

## D12. Datagen is deterministic and never writes to the api database (2026-10-28)
It writes what a college would upload (CSV/XLSX), the mockgov registries, demo users and `ground_truth.json`. `make seed` loads them through the api's own importer. From Week 2 student rows go through the real upload engine.

## D13. Parallel build with role-split agents on separate branches (2026-10-28)
Backend, frontend, UI, UX, progress and monitor roles each work on their own branch from a shared contract in `docs/ARCHITECTURE.md` and `docs/API_CONTRACT.md`. The contract is the only thing both sides may assume about each other.

## D14. An upload is a delta keyed by student identity (2026-10-28)
An upload carries one institution and one academic year and touches only the rows it contains. Each row upserts the enrolment keyed by (student identity, programme, academic year). Identity is the APAAR HMAC when a valid APAAR is given with consent, else the passport HMAC for an international student, else the institution's provisional match on normalised name, date of birth and mobile HMAC. Three optional columns, `status` (ACTIVE by default, WITHDRAWN or TRANSFERRED), `status_date` and `admission_date` (both ISO dates, defaulting to the upload date), let a college report withdrawals, transfers and late admissions without re-sending its roll. Re-uploading the same file changes nothing, and a bad row never aborts a file: it becomes an upload row error and the good rows proceed. Reason: colleges change their rolls all year; a delta with stable identity keys makes re-uploads safe and lets the Seat Ledger see releases and refills as events.

Extended by D42 on 2026-10-29: a saved column mapping, three eligibility columns, and a stored version for every change to an enrolment.

## D15. One pipeline function with a fixed stage order (2026-10-28)
`run_batch(batch_id)` runs parse and header check, row validation, within-file duplicates, upsert of students and enrolments, Seat Ledger, the five checks (adapter calls concurrent), cross-institution duplicates, flags, then marks the batch DONE with counts. The Celery task, the REST upload path and `make seed` all call it. Progress (`stage`, `total_rows`, `processed_rows`) is saved on `upload_batches` every 500 rows. Reason: one code path means the seeded demo and a live upload behave the same, and the order guarantees each engine finds what it depends on (checks need seats; duplicates need upserted students).

## D16. The Seat Ledger assigns seats in the database (2026-10-28)
The admission route picks the pool through `rules.yaml` `admission_routes`; the approval is the one for (programme, cohort year) from `app/core/cohort.py`. A seat is taken in one transaction with `SELECT ... FOR UPDATE SKIP LOCKED LIMIT 1` on FREE seats of that pool; CIWG-reserved seats go only to CIWG students and the INTERNATIONAL pool only to the INTERNATIONAL route. With no free seat the enrolment stays unseated and a flag is raised once per (institution, programme, cohort year, pool): EXCESS_ADMISSION (HIGH) for the REGULAR pool, QUOTA_BREACH for any other pool (MEDIUM, HIGH when INTERNATIONAL or NRI is exceeded by more than 2). Its evidence is refreshed as rows arrive ("132 admitted against 120 approved; 12 without a seat"). WITHDRAWN and TRANSFERRED release the seat back to FREE. A released seat assigned again after the approval's cutoff date (judged by `admission_date`) raises LATE_REFILL (MEDIUM). Seat events are append-only and every assignment and release is written to the audit chain. Reason: when every approved seat is a row, excess and quota breaches are counted by the database the moment a file lands; SKIP LOCKED keeps concurrent workers safe; the event log plus the hash chain give officers a tamper-evident seat history.

Partly superseded by D41 on 2026-10-29: pools follow the current approval version, and a CIWG student is one the upload marks CIWG.

## D17. Name matching is a pure, heavily tested module (2026-10-28)
`app/engine/matching.py` normalises names (lower case; honorifics mr, ms, mrs, dr, shri, smt, kumari, km and sri removed; punctuation stripped; spaces collapsed; Mohd, Md, Mohammad and Muhammad folded to mohammed; common spelling folds), transliterates Devanagari to Latin with indic-transliteration (ITRANS or IAST, then ASCII-folded) and matches tokens with awareness of initials on top of RapidFuzz, so "R. K. Sharma" and "Ravi Kumar Sharma" score at least 90 when the initials line up and the surname matches. Thresholds come from `rules.yaml`: 90 and above is a match, 75 to 90 needs review, below 75 is no match. Date of birth must agree for any identity or duplicate decision. Reason: Indian names arrive with honorifics, initials, spelling variants and in Devanagari, and plain fuzzy ratios score them too low; pure functions are cheap to test exhaustively, and thresholds in `rules.yaml` keep the cut-offs visible to the panel.

## D18. Five checks with fixed outcomes; an outage is never a failure (2026-10-28)
Each check in `app/engine/checks/` returns a status, a source and a detail with a plain-English `summary`. IDENTITY verifies the APAAR (NA without one, FAIL with INVALID_APAAR or NAME_MISMATCH, PENDING for review between 75 and 90). ADMISSION checks the counselling list for counselling, TFW and lateral admissions, the seat-type rules for management, spot and NRI admissions, and Study in India for international ones. SEAT passes when the enrolment holds one assigned seat in its cohort approval. STUDYING reads ABC credits for each completed year, from year 2 for a lateral entrant (NA in the first year, for a year-2 lateral entrant or without an APAAR; FAIL with NO_ACADEMIC_ACTIVITY when two or more expected semesters have no credits; PENDING when one does). STUDENT stays PENDING until the Week 3 student loop. A source that cannot be reached gives PENDING with `detail.source_unavailable`, never FAIL, and the recheck endpoints re-run PENDING checks. Score is passes over applicable checks (not NA); PENDING counts as applicable but not as a pass, shown as "n of m". Reason: one independent source per check lets an officer see exactly which source disagreed, and treating an outage as pending means a government system going down never flags a genuine student.

Superseded by D34, D35 and D39 on 2026-10-29: the five checks become evidence rows with six states and provenance, the ADMISSION row reads the joining record, and the score is replaced by the record status.

## D19. Duplicates: exact within a file, blocked and fuzzy elsewhere (2026-10-28)
`app/engine/duplicates.py`. An APAAR repeated within one file is a row error, DUPLICATE_IN_FILE, and the later row is rejected. Within an institution, records without an APAAR are blocked on (date of birth, first initial, metaphone of the surname) and a pair whose names score 90 or more with initials awareness, or that share a mobile HMAC, raises DUPLICATE_WITHIN_UPLOAD (MEDIUM) linking both enrolments (the "R. K. Sharma" demo). The same APAAR ACTIVE at two institutions in one academic year raises DUPLICATE_CROSS_INSTITUTION (HIGH), unless one programme is PHYSICAL and the other ODL or ONLINE, which raises DUAL_ENROLMENT_ALLOWED (LOW) and cites the UGC 2022 rule. Without an APAAR across institutions, the same block plus a name score of 90 or more plus the same mobile HMAC raises DUPLICATE_CROSS_INSTITUTION (MEDIUM). This needs `programmes.mode` (migration 0002); the seed imports datagen's `mode`. Reason: a repeated id inside one file is a clerical error the college fixes itself, while everything across records needs evidence and an officer; blocking keeps comparisons near linear; and the UGC rule makes one physical plus one distance programme lawful, so it must not read as a duplicate.

## D20. Flags are made by engines, deduplicated and never deleted (2026-10-28)
Only engines create flags. Each carries a `dedupe_key`, so a re-run updates the existing flag instead of adding one; flags are never deleted and start OPEN. Evidence has one schema: `{summary, facts: [{label, value, source}], related_enrolment_ids, rule_source?}`, where `summary` is one plain-English sentence from the copy deck templates. Week 2 exposes read endpoints only; officer actions arrive in Week 3. Reason: an officer must be able to trust that a flag reflects the data and was not added or removed by hand; dedupe keys make every engine safe to re-run; one evidence shape lets the web render any flag without special cases.

Partly superseded by D45 on 2026-10-29: an officer may open a case from a signal; every other case is still made by an engine.

## D21. Dashboard KPIs from real flags and checks (2026-10-28)
`kpis.flags_open` counts real flags. `kpis.countersigned_pct` is the share of ACTIVE enrolments whose applicable checks are all PASS; `kpis.clear_pct` is the share with no FAIL. The institutions list sort `flags_open_desc` becomes real. Reason: the share fully countersigned is the headline number; with the student check pending until Week 3 it stays below 100 percent, which is the true state, and the clear share shows how much of the roll no source contradicts.

Superseded by D35 and D46 on 2026-10-29: `countersigned_pct` is the COUNTERSIGNED share of active records and `clear_pct` is gone.

## D22. The seed goes through the engine, against a time budget (2026-10-28)
`make seed` seeds mockgov first, then runs every datagen upload through `run_batch` in-process (no Celery), so the Makefile order changes. Target: the small seed (about 10.5k rows) in under 3 minutes. 50k rows in under 2 minutes is the Week 4 evaluation target; it is measured and recorded now. Reason: the demo data must come from the same engine the panel is shown, and measuring early tells us whether Week 4 needs bulk paths.

## D23. Every active enrolment gets a student notice after its upload (2026-10-28)
When an upload batch reaches DONE, a separate background task (`countersign.send_notices`) sends the notices, so finishing a batch is never delayed by mail. Every ACTIVE enrolment in the batch that has no live or answered notice gets one, whatever its Identity result. A notice goes by email when the college gave an email address and to the student's DigiLocker inbox when the student has a linked APAAR; each channel has its own row and its own link token (32 random bytes, URL-safe), of which only the SHA-256 hash is stored. Links read `{WEB_ORIGIN}/student/notices/{token}` and expire after `notices.expiry_days` in `rules.yaml` (30). Each delivery is recorded as QUEUED, SENT or FAILED and tried up to three times with a pause between tries; a DigiLocker outage never holds up email, and a DigiLocker answer that the APAAR has no account marks that delivery FAILED. The mailer refuses any SMTP host outside `SMTP_ALLOWED_HOSTS` (by default `mailpit`, `localhost` and `127.0.0.1`) unless `ALLOW_REAL_SMTP=true`, which the project never sets, and opens one SMTP connection per 500 messages. When an enrolment has no live notice and no reply (every notice expired or failed), the college (for its own students) or an officer may resend it, at most three times per enrolment and academic year. A student who has withdrawn notice consent gets no new notices. Reason: the notice is how the real APAAR holder learns that their identity was used, so it must reach the student even, and especially, when Identity failed; storing only a hash means a copy of the database cannot answer a notice; and the SMTP allow-list, like the rule for government APIs, keeps the demo from ever writing to a real person.

Partly superseded by D37 on 2026-10-29: a notice only points the student to DigiLocker sign-in; who gets one and how it is delivered are unchanged.

## D24. The Student check comes only from the notices, and a No beats a Yes (2026-10-28)
The STUDENT check (source `STUDENT_NOTICE`) is derived from the enrolment's notices, never from an adapter. No notice sent yet, a notice sent and not answered, and a notice that expired without a reply all leave it PENDING with a neutral sentence: no reply is never a failure and never a flag. A student with no email address and no linked APAAR cannot be sent a notice; the check stays PENDING ("No email or APAAR on record, so no notice can be sent."), not NA, so a college cannot avoid the check by leaving out contact details. A Yes on any channel makes it PASS. A No on any channel makes it FAIL and raises STUDENT_DENIED (HIGH, one per enrolment), and a No beats a Yes, because the college supplies the email address while DigiLocker is tied to the APAAR holder. The flag's evidence gives the channel, the date the notice was sent and the date of the reply; the student's comment is a fact for officers only, so a registrar never sees it. The student may change an answer once within 7 days of the first reply. No to Yes makes the check PASS, but the flag keeps its status (only officers resolve flags) and gets refreshed evidence and a system note in its history; Yes to No makes the check FAIL and raises the flag. The countersign score and the dashboard use the new status at once. A Yes also records the student's notice consent. Reason: silence proves nothing either way, so it must never count against a genuine student; a denial is the strongest sign of identity misuse the product can collect, so it goes to an officer with the student's own words; and a short window to correct a mistaken tap stops one slip from turning into a case while the officer still sees what happened.

Superseded by D37 on 2026-10-29: a reply is recorded only from a student signed in through DigiLocker. The derivation from the notices, a No beating a Yes and the one change within 7 days stay.

## D25. Officers act on flags through a fixed table of transitions (2026-10-28)
Officers act with `POST /flags/{id}/actions`, giving an action and a note (ASSIGN has none). Notes on clearing, requesting documents and confirming are shown to the college; notes on escalating, adding a note and reopening stay with officers, and the college sees those history rows without them. From OPEN or DOCS_REQUESTED a flag can move to DOCS_REQUESTED (request documents), ESCALATED, CLEARED or CONFIRMED. From ESCALATED only an AICTE officer can move it to DOCS_REQUESTED, CLEARED or CONFIRMED. CLEARED and CONFIRMED are final, except that an AICTE officer may reopen a flag, with a note, which sends it back to OPEN. Adding a note and assigning an officer never change the status. A regional officer acts on flags of institutions in its region, but on an escalated flag may only add notes. A college may only respond, with a note and up to three PDF, PNG or JPEG files of at most 5 MB each, while its own flag is DOCS_REQUESTED; the response keeps that status and marks the flag as answered. Universities never act on flags. A wrong role gets 403, a flag outside the caller's scope 404, and a move the table does not allow 409 `FLAG_TRANSITION_INVALID`. Requesting documents emails every registrar of the college and records the due date on the flag. Confirming changes nothing on the enrolment and deletes nothing; it revokes any active credential issued for the flag's enrolment, and the confirmation sheet says so. Engines still never change a flag's status; when they refresh the evidence of a cleared or confirmed flag, a system note says so in the history. Attachments are stored outside the database under random names with their SHA-256 and are served only through a scoped, audited download. Every action is a `case_actions` row, so a flag's history shows who did what, when and why. Reason: a fixed table with role rules makes the case record predictable and testable; an escalation means a senior officer takes over, so the regional office cannot quietly undo it; and leaving the enrolment untouched on confirmation keeps the rule that nothing is auto-rejected, with the decision recorded instead.

Superseded by D43 on 2026-10-29: CLEAR and CONFIRM become UPHOLD and WITHDRAW, CORRECT is added, every decision carries a reason code, and a decision changes the record, its seat and its attestation together.

## D26. Student-held credentials are SD-JWTs signed by Countersign (2026-10-28)
Credentials use the `sd-jwt` reference library (SDJWTIssuer, SDJWTHolder, SDJWTVerifier) with ES256 keys from `jwcrypto`. The issuer key is a `signing_keys` row whose private part is Fernet-encrypted with `PII_FERNET_KEY` and whose `kid` is the JWK thumbprint; it is created on first use and only one is active. The issuer publishes `/.well-known/jwks.json`, `/.well-known/jwt-vc-issuer` (`{issuer, jwks_uri}`) and an IETF Token Status List at `/status-lists/1` (one bit per credential, 131,072 entries, compressed and cached for 60 seconds); the issuer URL comes from `ISSUER_URL`. An Enrolment proof is issued automatically when the enrolment's Student check is PASS, no check is FAIL and no unresolved HIGH flag names the enrolment; eligibility is looked at again after a recheck and after a case is cleared, and there is at most one active credential per enrolment and kind. The signed claims always in view are the issuer, issue time, expiry (31 August after the academic year ends), the credential type `countersign:enrolment:v1`, the status-list entry and the holder's public key; name, date of birth, masked APAAR, institution, programme, academic year, year of study and the list of countersigned checks with their date are selectively disclosable. Each student has an ES256 holder key, kept encrypted on the server because the demo wallet is custodial; a real deployment keeps it on the student's phone. To share, the student ticks fields and agrees to the share text, and the server builds the presentation with institution and programme always disclosed and a key-binding JWT whose nonce is a one-time share code (six groups of four Crockford base32 characters) and whose audience is `{ISSUER_URL}/verify`; it is kept for 10 minutes and returned as a code, a link and a QR. A credential's status-list index is a random unused one. A credential is revoked when its enrolment is withdrawn or transferred, when a flag on its enrolment is confirmed, or by an AICTE officer with a reason, and never because a check is pending; each revocation carries a reason code (ENROLMENT_WITHDRAWN, ENROLMENT_TRANSFERRED, FLAG_CONFIRMED or ADMIN) so the wallet can explain it in plain words. Reason: selective disclosure lets a student prove an enrolment to an employer without handing over the whole record; a standard format with published keys lets anyone verify a proof without querying Countersign about the student; and a status list shows revocation without telling a verifier who else holds a credential.

Partly superseded by D44 on 2026-10-29: an Enrolment attestation is issued when the record is COUNTERSIGNED and revoked when the record is withdrawn, disputed or revoked by an officer. The format, keys, status list and sharing stay.

## D27. Anyone can verify a proof without an account (2026-10-28)
`GET /verify/{code}` is public and rate-limited. It loads the stored presentation and checks it with the library's verifier, using a key lookup that reads the same JWKS document a third party fetches, with the share code as the expected nonce and `{ISSUER_URL}/verify` as the expected audience; it then checks the expiry and the status-list bit. `POST /verify` checks a pasted raw SD-JWT presentation the same way (issuer signature, key binding signature, expiry, status) and reports its nonce without enforcing it. The answer is VALID, REVOKED, EXPIRED or INVALID, with the credential kind, the issuer, the issue date, the disclosed fields with their labels, whether the proof is bound to the holder's key and when the status was checked. The verifier never returns a claim the student did not disclose, never a full APAAR, and offers no search. Each verification is counted on the presentation, so the student's wallet shows "Shared with a verifier at 10:42". The web page scans with the browser's BarcodeDetector where it exists and otherwise takes a typed or pasted code. Reason: an employer or admissions office should need nothing but a phone to check a proof; tying the key binding to the one-time code stops a copied presentation from being replayed under another code; and returning only what the student chose keeps the student in control of what is shown.

## D28. Degrees carry a masked APAAR and a compact signed QR (2026-10-28)
Graduates are seeded from datagen `graduates.jsonl`: final-year students of 2025-26 at institutions affiliated to each university, stored as GRADUATED enrolments of 2025-26 with no seat, no checks and no flags; most have an APAAR and a few only a provisional id. A university lists the graduates of its own affiliates (an AICTE officer sees all) with `GET /university/graduates` and issues a Degree proof with `POST /university/degrees/{enrolment_id}/issue`. The proof is an SD-JWT in the student's wallet without a holder key, because a printed proof cannot be bound to a phone, plus a compact JWS (ES256, the issuer key, `kid` in the header) over `{v, cid, n, p, i, u, y, a}`: version, credential short id, name, programme short name, institution short name, university code, year of award, and the last four APAAR digits or a masked provisional id. The QR encodes `{WEB_ORIGIN}/verify/d/{jws}`, about 350 characters, so it stays small enough to print and scan. `GET /verify/d/{jws}` checks the signature against the JWKS and the credential's revocation bit. `GET /university/degrees/{enrolment_id}` returns the print data with the QR as SVG, and `GET /university/degrees/{enrolment_id}/insert.pdf` renders a sample A4 degree insert (reportlab) with the masked APAAR and the QR. The web print view is `/university/degrees/[enrolmentId]/print`. The insert also prints the proof's short id under the QR, and `GET /verify/degree/{short_id}` answers from AICTE's own record for a reader who cannot scan, saying that it checked the register rather than a signature. Reason: a degree certificate is read offline by people with no Countersign account, so its QR must carry a self-contained signed claim; keeping the payload short keeps the printed code legible; and the masked APAAR lets a reader match the paper to the person without exposing the full id.

Superseded by D44 on 2026-10-29: Countersign issues no degree. The Degree proof becomes a completion attestation behind certificate integration for the awarding body; the compact QR and the masked APAAR stay.

## D29. Sensitive reads join the audit chain, and the chain can be checked in the browser (2026-10-28)
Writes have been chained since D7. Week 3 adds READ entries for notice page views (no actor, marked as coming through the notice link), credential reads and shares, verifier calls (no actor, with a keyed hash of the caller's IP address), attachment downloads, enrolment detail views and student data exports. `GET /admin/audit` gains `entity_id`, `action` and `seq_from` filters, and `GET /admin/audit/verify` keeps reporting `first_broken_seq`. The AICTE officer's `/admin/audit` page lists the chain, has a Verify chain button and highlights the first broken entry. For the demo, `make audit-tamper SEQ=n` edits one stored entry from the command line and refuses unless `DEMO_MODE=true`; `make demo-reset` rebuilds a clean chain. Reason: privacy by design means being able to show who looked at a student's record, not only who changed it; and editing one entry in front of the panel is the only convincing way to show that the chain detects tampering.

## D30. Consent is stored with its exact text, and students can act on their own data (2026-10-28)
`consents` rows record APAAR linking from the college's upload (the college upload channel), notice consent when the student answers Yes, and share consent every time a proof is shared, each with the exact text shown and its `notice_version`. The privacy notice is versioned in `app/privacy/notice.py` and served publicly at `GET /privacy/notice`. A student lists their consents with `GET /students/me/consents` and may withdraw notice consent (no new notices; notices already sent can still be answered) or share consent (every live proof expires at once). Unlinking an APAAR is a correction request, because the college must upload the record again, and admission is never blocked. `GET /students/me/access-log` lists the READ entries about the student and their enrolments with the reader's role and the date only, never a name. An access request is fulfilled at once by `GET /students/me/export.json`, everything held with the APAAR masked. Correction and erasure requests go to AICTE officers through `GET /data-requests` and are resolved as DONE or REJECTED with a written response; an erasure response explains which records the law requires AICTE to keep. Masking stays everywhere. Reason: the DPDP Act gives students rights of access, correction and withdrawal that must be usable, not only described, and keeping the exact text a student saw is the only way to show what they agreed to.

## D31. The seed sends real notices and applies simulated replies (2026-10-28)
`make seed` loads mockgov, imports the institutions, runs every upload through `run_batch`, imports the graduates, sends the notices for every batch (Mailpit and the mock DigiLocker inbox), and then runs `python -m app.seed.replies --from /data/generated`, which applies datagen's `notice_replies.jsonl` through the same service the public notice page uses (no actor, marked as the demo seed). About 70 percent of clean enrolments answer Yes, every planted denial answers No, and the rest do not reply. Ravi Kumar Sharma (the `student@demo` login) and one more named student are left unanswered so the demo can answer live from Mailpit. Mailpit keeps 20,000 messages. Ground truth gains nothing: the STUDENT_DENIED cases (8 in the small size) were already planted, and the quick check must still find every planted case with no unexplained flag. Reason: the countersigned share on the dashboard and the denial cases should come from the same code a real reply takes, and leaving the demo student unanswered keeps the live moment in the demo.

Partly superseded by D37 on 2026-10-29: the seeded replies stand for replies made after DigiLocker sign-in.

## D32. Public rate limits and the Week 3 error codes (2026-10-28)
Public routes are limited per client address: `/notices/*` 30 requests a minute, `/verify` and `/verify/*` 60, `/.well-known/*` and `/status-lists/*` 120. New error codes: `NOTICE_NOT_FOUND` (404, the same body for a malformed and an unknown token), `NOTICE_EXPIRED` (410), `NOTICE_ALREADY_CHANGED` (409), `FLAG_TRANSITION_INVALID` (409), `ATTACHMENT_TOO_LARGE` (413), `ATTACHMENT_TYPE` (415), `CREDENTIAL_NOT_ELIGIBLE` (409), `CREDENTIAL_REVOKED` (409), `PRESENTATION_NOT_FOUND` (404), `RESEND_LIMIT` (429) and `NOTICE_LIVE` (409). Reason: notice links and share codes can only be guessed by brute force, and the limits make guessing pointless; giving the same answer for malformed and unknown tokens tells an attacker nothing; and one code per situation lets the web show the right sentence without reading messages.

## D33. The demo path is an end-to-end test (2026-10-28)

## D34. Every fact on a record carries an evidence state and its provenance (2026-10-29)
An enrolment is a claim, and it has five evidence rows: Identity, Seat, Joining record, Credits and Student (wire names IDENTITY, SEAT, ADMISSION, STUDYING, STUDENT, unchanged). Each row carries exactly one evidence state: CONFIRMED, CONTRADICTED, PENDING, NOT_YET_DUE, NOT_APPLICABLE or SOURCE_UNAVAILABLE. These replace the `checks_status` values: PASS becomes CONFIRMED, FAIL becomes CONTRADICTED, NA becomes NOT_YET_DUE when the reason is that no semester result exists yet (a first-year, or a lateral entrant in year 2) and NOT_APPLICABLE otherwise, PENDING with `detail.source_unavailable` becomes SOURCE_UNAVAILABLE, and every other PENDING stays PENDING. Every row also records its provenance: `supplied_by`, the source in words ("APAAR registry", "AICTE approval v2, 2026-27 (Seat Ledger, derived)", "State admission authority", "ABC, issued by Maharashtra State Technical University", "Student via DigiLocker sign-in", "Study in India"); `observed_at`, when that source supplied the fact; and `independent`, true when the fact does not come from the institution that made the claim (D38). NOT_YET_DUE covers credits before the first semester result and the joining record before the reporting deadline while the authority has not published it. SOURCE_UNAVAILABLE replaces "pending because the source did not answer" and never contradicts anything. A name similarity from 75 to 89 is PENDING with `needs_review`: name matching supports a decision and never makes one. Reason: an officer, a college and a panel must see for each fact who said it, when, and whether that source is independent of the college; six named states say plainly what is missing instead of folding it into a score, and an outage stays visibly different from a contradiction.

## D35. One evidence rule gives every record one status (2026-10-29)
Each ACTIVE enrolment has exactly one record status, computed by one pure function (`app/engine/status.py`) from its five rows, the unresolved cases that name it and the officers' resolutions on its rows. In order of precedence: DISPUTED when the Student row is CONTRADICTED and the student's dispute (a STUDENT_DENIED case) is unresolved; UNDER_REVIEW when any row is CONTRADICTED and not resolved by a decision, or any case naming the record is unresolved (OPEN, DOCS_REQUESTED or ESCALATED), whatever its severity; COUNTERSIGNED when Identity is CONFIRMED (through APAAR, Study in India or the alternative route of D36), Seat is CONFIRMED, at least one of Joining record, Credits and Student is CONFIRMED and independent, and nothing is unresolved; AWAITING_EVIDENCE otherwise. There is no score and no "n of 5": one contradiction outranks any number of confirmations. The status is stored on `enrolments.record_status` with `status_reason` (one sentence naming the deciding row or case) and `next_step` (one sentence taken from the open case's last action, such as "College asked for admission documents by 29 Aug 2026.", or from the first missing evidence, such as "Waiting for the joining record from the state admission authority."), and it is recomputed in the same transaction as any change to a row, a case or the enrolment. Every CONTRADICTED row has a case an officer can decide: IDENTITY raises INVALID_APAAR or NAME_MISMATCH, SEAT raises EXCESS_ADMISSION, QUOTA_BREACH or ELIGIBILITY_BREACH, ADMISSION raises NOT_IN_JOINING_RECORD (MEDIUM), STUDYING raises NO_ACADEMIC_ACTIVITY and STUDENT raises STUDENT_DENIED, shown as "Student dispute" (HIGH). Dashboards count records by status, and `countersigned_pct` becomes the COUNTERSIGNED share of active records. Reason: this is the deck's evidence rule, "Countersigned = identity verified (or the alternative route) + seat fits the approval + at least one piece of enrolment evidence independent of the college + nothing unresolved"; a score lets four agreements outvote a student who says "not me", and the rule does not; recomputing in the same transaction means no page can show a status that disagrees with its rows and cases.

## D36. Identity has an alternative route, and admission is never blocked (2026-10-29)
With a linked APAAR, the Identity row is the APAAR registry check, as before. Without one (consent refused or pending), the alternative route is the student signing in through DigiLocker and claiming the record with the provisional ID the college gave them: the date of birth on the DigiLocker identity must equal the record's and its name must reach the review threshold (75) against the record's name; name matching supports the claim, the DigiLocker sign-in decides it. Identity then becomes CONFIRMED with `supplied_by` "Student via DigiLocker sign-in". Until then Identity is NOT_APPLICABLE ("APAAR not linked; alternative route not used yet.") and the record stays AWAITING_EVIDENCE: never invalid, and admission is never blocked. The APAAR on a DigiLocker identity is used only to find a student who already has that APAAR with consent LINKED; it is never stored on a student whose consent is not LINKED. For an international student, Study in India by passport is both the identity and the admission source. Reason: the Supreme Court's APAAR order requires that refusal is honoured, so a student without APAAR needs a route to a countersigned record that does not depend on APAAR, and an identity the government already authenticates (DigiLocker) is that route.

## D37. A student answers only after signing in through DigiLocker (2026-10-29)
mockgov gains a simulated DigiLocker OAuth: `GET /digilocker/oauth/authorize` is a plain sign-in page labelled "Demo DigiLocker" where the user picks a synthetic account by APAAR or DigiLocker id and types the OTP 123456, and `POST /digilocker/oauth/token` returns a signed id token with the DigiLocker subject, name, date of birth and the APAAR when one is linked. The api's `GET /auth/digilocker/start` and `GET /auth/digilocker/callback` sign a STUDENT in; the account is created on first sign-in and bound to the student by APAAR, or by provisional ID through `POST /auth/digilocker/claim` (D36), and `users.digilocker_sub` holds the DigiLocker subject. The notice link, by email or in the DigiLocker inbox, opens the claim page; it shows the claim to anyone holding the link, but its Yes and No buttons need DigiLocker sign-in, and the signed-in identity must be the record's student (by APAAR, or by a provisional-ID claim), otherwise the page says "This notice is for someone else." and nothing is recorded. A signed-in student can also answer from their own enrolments. A reply made any other way does not exist any more: email is only a pointer. The password login for students is removed; the login page offers "Sign in with DigiLocker" and the demo DigiLocker page lists Ravi Kumar Sharma first. The seed's planned replies are recorded as replies made after DigiLocker sign-in. Reason: the college supplies the email address, so a reply through an emailed link proves only that someone read that mailbox; the deck's answer to "what if a college uploads its own phone numbers for students?" is that students confirm only after signing in through an independent route.

## D38. Independence comes from the issuer of each fact (2026-10-29)
A fact is independent when its issuer is not the institution that made the claim. The state admission authority, the APAAR registry, Study in India and the student's DigiLocker sign-in are independent. ABC credits are independent only when the issuing body (`abc_credits.issuer`) is not the claiming institution, for example the affiliating university; credits a college issued for itself are shown CONFIRMED with `independent: false` and never satisfy the evidence rule on their own. The Seat row is derived from the college's own upload against AICTE's approval, so it is never counted as independent enrolment evidence (the rule asks for it separately). mockgov's ABC records carry the issuer, and datagen makes its autonomous colleges issue their own credits. Reason: the deck names "credits uploaded by the same college that made the claim" as a challenge; the only honest answer is to look at who issued each record and to refuse to count a college's word as evidence for the college.

## D39. The Joining record row reads the state admission authority's joining record (2026-10-29)
The ADMISSION row checks the state admission authority's joining record (the student reported and joined at this college, in this programme), not only the allotment: mockgov `POST /admission-authority/joining {state, academic_year, name, dob, roll_no?, institution_code, programme}` answers `{found, joined_on, round, route, category}` plus `published`, false when the authority has published nothing for that state and year. One state's record format is simulated and served for every state, labelled as a simulator. Management, NRI and spot admissions appear in the authority's approved-admissions list too, as the state regulators approve them, so every route except INTERNATIONAL reads the joining record; international admissions read Study in India. Found is CONFIRMED and independent. Not found is CONTRADICTED (with a NOT_IN_JOINING_RECORD case) only after the reporting deadline (D40); before it the row is PENDING ("Not in the joining record yet"), or NOT_YET_DUE while the authority has published nothing. The counselling-list call is no longer made. Reason: an allotment proves a seat was offered, not that the student turned up; the joining record is the earliest independent evidence that a specific enrolment is real.

## D40. Completeness per college, against the authority and the reporting deadline (2026-10-29)
The admission authority also lists every joining per institution (`GET /admission-authority/joinings?institution_code&academic_year`). Each institution and year is reconciled: students who joined but are missing from the college's upload, and students uploaded but never joined (already CONTRADICTED Joining record rows). `completeness = uploaded_and_joined / joined` per college, shown with the number missing. The reporting deadline per academic year comes from `rules.yaml` (`reporting.deadline`, 30 Sep 2026 for 2026-27) and gives each college a deadline state from its first completed upload: ON_TIME, LATE, OVERDUE (none yet and the deadline has passed) or NOT_DUE. Missing students raise one MISSING_FROM_UPLOAD case per college and year (MEDIUM) that lists them by masked id and names no record. The reconciliation is stored per institution and year in the existing `institution_scores` table, which held the Integrity Index (now dropped) and keeps its columns. Datagen plants colleges that leave students out, upload late, or do not upload. Reason: the deck's answer to "what if a college simply doesn't upload some students?" is reconciliation, deadlines and a completeness score per college; Countersign can only check data it receives, and completeness makes the gap visible instead of hiding it.

## D41. Seats follow the versioned approval, and each seat type checks eligibility (2026-10-29)
`approval_versions` holds every version of an approval (version, approved intake, effective from, source) and `approvals.current_version` names the current one. Only an AICTE officer adds a version. One that raises intake adds seats and re-seats the backlog; one that lowers it removes free seats and is refused when a pool would fall below its assigned seats. Seat rows cite the version: "AICTE approval v2, 2026-27 (Seat Ledger, derived)". Category eligibility is checked from what the college reported (new upload columns `tfw_income_certified`, `nri_sponsored`, `ciwg`, stored in `enrolments.eligibility`): the INTERNATIONAL pool is for foreign nationals, OCI and PIO students, and for an Indian national only when marked CIWG (and the CIWG-reserved third only for CIWG students); the NRI pool only for rows marked NRI or NRI-sponsored; TFW only with `tfw_income_certified = yes`, and the Seat row is PENDING ("TFW income certificate not reported.") when the column is blank. A breach makes the Seat row CONTRADICTED with the handbook clause and raises ELIGIBILITY_BREACH (MEDIUM). Reason: capacity changes during the year through revised approvals, and the deck commits to checking capacity against the versioned approval and the handbook's category rules, not against one number frozen at upload time.

## D42. A college maps its columns once, and every change to a record is a version (2026-10-29)
A college maps its own column names to the template once (`GET` and `PUT /institutions/{id}/column-mapping`); later files with those headers are mapped automatically, the mapping used is shown on the batch, and a file whose unknown headers leave a required column missing is answered with `UPLOAD_HEADER_UNMAPPED` and the headers to map. Rows still match existing people and enrolments by stable keys (D14: internal ids, with APAAR as an attribute). Every change to an enrolment, by an upload, by an officer's correction or by the seed, is stored in `enrolment_versions` (the changed fields before and after, the batch or the case action, the actor and the time) and shown as the record's history. Reason: the deck promises one upload in a college's own format and safe re-uploads; versions let an officer see what changed, when and on whose word, which is what makes a correction accountable.

## D43. Officer decisions change the record, the seat and the attestation together (2026-10-29)
Case outcomes are UPHELD (the college's claim stands; the case is closed), CORRECTED (the officer corrects named fields of the record; the correction is stored as a version and the record's rows and the Seat Ledger run again), WITHDRAWN (the claim is withdrawn: the enrolment becomes WITHDRAWN "by decision", its seat is released and its attestation revoked) and ESCALATED (to AICTE). REQUEST_DOCS, NOTE, ASSIGN and REOPEN stay. The `flags_status` values CLEARED and CONFIRMED are renamed UPHELD and WITHDRAWN and CORRECTED is added; the actions CLEAR and CONFIRM become UPHOLD and WITHDRAW and CORRECT is added. Every decision needs a reason code and a note. Decisions resolve contradictions; they are not evidence: after UPHOLD the row keeps its CONTRADICTED state with `resolved` (outcome, officer, time) and no longer counts as unresolved, so an upheld record still needs an independent CONFIRMED row to be COUNTERSIGNED; after CORRECT the row is evaluated again on the corrected record; after WITHDRAW the enrolment leaves the active counts. Programme-level cases (excess admission, quota breach) take WITHDRAW or CORRECT per named enrolment, and close when no named record is left undecided, or take UPHOLD when a new approval version covers them. The record status, the seat count, the attestation, the version and the audit trail change in one transaction; nothing changes without an officer. Reason: the deck's hero is a dispute that ends in an accountable decision that changes the actual system; a decision recorded beside an untouched record (D25) left the seat count and the attestation telling a different story.

## D44. Countersign attests enrolments; awarding bodies get certificate integration (2026-10-29)
User-facing words are "attestation" (not credential or proof), "case" (not flag) and "dispute" for a student's "I never joined"; wire paths and enum names stay as they are. Countersign issues enrolment attestations only, and the one eligibility rule is that the record is COUNTERSIGNED. An attestation is revoked when its record leaves ACTIVE through a withdrawal, when an officer revokes it, or when the record becomes DISPUTED; a pending row never revokes. An officer's revocation holds (Addendum 3 errata 11), and a record that returns to COUNTERSIGNED after a dispute is upheld gets an attestation again only if its earlier one was revoked by the dispute. Degrees come from the awarding body: the DEGREE kind becomes COMPLETION ("completion attestation"), and the university page becomes certificate integration: an API and a print view that give the awarding body the masked APAAR and a compact signed QR pointing to the completion attestation, for its own certificate. Reason: the deck's answer to "are you issuing degrees?" is no; an attestation that follows the evidence rule means a shared attestation says exactly what the record card says.

## D45. Signals are for officers only and never set a status (2026-10-29)
Two detectors produce signals. GHOST_RING: a NetworkX graph of students linked by a shared mobile, email or address hash; a component of 3 or more students across 2 or more colleges, or of 5 or more in one college, is a signal with its members and the shared contacts. ANOMALY: a scikit-learn Isolation Forest per academic year over the institutions, with admission growth, NRI share, management share, contradiction rate and contact-sharing rate as features; the outliers become signals with the feature values that made them stand out. Signals live in a `signals` table, are visible to AICTE and regional officers only (a regional officer sees those touching its region), never change a record's status, rows or cases, and an officer can open a case from one (the case cites the signal, and from then on follows the rules of D35 and D43 like any other) or dismiss one with a note. Each signal carries a plain sentence, its facts and the rule or model that produced it ("Isolation Forest, contamination 5%, trained on this year's 50 colleges"). Reason: patterns across records can point an officer at something, but they are not evidence about one enrolment; keeping them out of the status keeps the deck's promise that every status comes from published rules and every decision is an officer's.

The college dashboard shows its records by status, its missing students, the cases against it and its deadline. Reports under `/reports/*`, scoped for AICTE and regional officers: by state, by institution type, cases by type and outcome, countersign coverage and completeness, each as CSV and XLSX and as a one-page PDF, plus a one-page PDF summary. Every chart has its table beside it, charts are bar charts only, and there is no map. Reason: the PS asks for real-time dashboards and reports for policy and accreditation; counting the same statuses everywhere keeps the dashboard, the report and the record card in agreement.

## D47. The evaluation measures the product on synthetic data (2026-10-29)
`tools/eval`, run by `make eval`, rebuilds the databases, runs datagen and the engine, and writes `eval_report.md` and `eval.json`, every number labelled synthetic: detection of seeded inconsistencies (recall per type and severity match), wrong cases on legitimate records (false-alarm rate over known-clean records), processing time per upload and for 50,000 rows (target under 2 minutes), officer review effort (cases per 1,000 records, evidence facts per case), signal precision and recall against planted rings and anomalies, and cross-college access attempts (every institution user requesting every other institution's records, all refused). Targets: seeded inconsistencies caught at 95% or more, false alarms under 5%, 50,000 rows under 2 minutes, every cross-college attempt refused. Reaching the throughput target is part of the work: bulk evidence evaluation, concurrent adapter calls and fewer round trips. Reason: the deck promises a synthetic test bed that measures wrong flags, detection, processing time, review effort and cross-college access; a number the panel can rerun is worth more than a claim.

## D48. Private set intersection is a stretch, done last (2026-10-29)
`services/psi` (platform linux/amd64, openmined.psi) runs two mock regulators, AICTE and UGC, that learn only the overlap of their APAAR hash sets, with an `/admin/psi` page. It is built only if disk space allows (checked with `df` first); otherwise it is skipped and the reason recorded. Reason: it is the deck's Phase 2 item and depends on an amd64-only wheel that is expensive on the build machine; nothing else depends on it.

Built (2026-10-29, 7.2 GB free before the build). One linux/amd64 image (`openmined.psi` 2.0.6, which has no linux arm64 wheel; about 320 MB unpacked) runs as two containers: `psi`, the mock UGC, holds its own set, drawn from datagen's APAAR registry (a seeded 4% of it plus 8,000 seeded APAARs outside it, as HMACs under `PII_HMAC_KEY`); `psi-client` is Countersign's side, because the api's arm64 image cannot load the library: the api hands it the APAAR HMACs of linked students for one run, and only the encrypted request reaches `psi`. The cardinality variant (`reveal_intersection` false) means Countersign learns the overlap's size, never its members, and the partner refuses a request that asks for them. `POST /psi/compute` (AICTE_ADMIN, API_CONTRACT §A4.26) returns the three counts and audits them; `/admin/psi` shows them.
